## О проекте
 
**Boyler** — легковесная платформа для запуска изолированных процессов, контейнеров. Реализует базовый функционал контейнеризации: сетевая виртуализция, загрузка образов с  DockerHub, монтирования файловой системы, настройка namespaces и ограничение ресурсов через cgroup2.

Проект построен по архитектуре, близкой к Docker, но с упрощениями и собственными архитектурными решениями. Cпроектирован как модульная система из трёх независимых компонентов, что упрощает поддержку, тестирование и дальнейшее масштабирование — от локальной разработки до развёртывания на выделенном сервере с несколькими изолированными workload'ами.
 
## Возможности
 
- 📥 **Загрузка образов** — скачивание образов (пока только Linux-дистрибутивов) из проверенных реестров
- 🌐 **Сетевая виртуализация** — подключение контейнеров к виртуальному Linux bridge через veth-пары
- 🔒 **Изоляция namespaces** — полноценная изоляция через `cgroups`, `pid`, `mount` и другие namespaces
- 💾 **Монтирование образов** — собственная реализация overlay-монтирования файловой системы контейнеров
- ⚙️ **Управление** - gRPC API для управления жизненным циклом контейнеров и образов
- 🖥 **CLI** | Единая точка входа для пользователя — совместимый по духу с `docker` набор команд и UI

## 🏗 Архитектура

Boyler спроектирован по модульному принципу: вся система разбита на **три независимых бинарных файла**, каждый из которых решает свою узкую задачу и может собираться, тестироваться и обновляться отдельно от остальных.

### Компоненты

| Бинарник | Роль | Аналог в Docker |
|---|---|---|
| **`boyler-cli`** | Пользовательский интерфейс — точка входа для всех команд, взаимодействует с демоном по gRPC | `docker` CLI |
| **`boylerd`** | gRPC-демон — управляет образами, файловой системой и сетью контейнеров | `dockerd` + `containerd` |
| **`myrunc`** | Низкоуровневый рантайм — отвечает только за запуск процессов и применение изоляции namespaces | `runc` |

### Ключевое архитектурное отличие от Docker

В экосистеме Docker логика разделена на **три отдельных слоя**: `dockerd` (демон верхнего уровня, работа с API и пользовательскими командами), `containerd` (управление образами, снапшотами и жизненным циклом контейнеров) и `runc` (низкоуровневый запуск процессов по спецификации OCI).

В Boyler эта модель сознательно упрощена: функциональность `dockerd` и `containerd` **объединена в одном компоненте — `boylerd`**. Демон одновременно отвечает и за приём команд от CLI, и за управление образами, файловой системой (overlay-монтирование) и сетью контейнеров.

Такое решение снижает количество межпроцессных взаимодействий и упрощает архитектуру, но при этом сохраняет чёткое разделение ответственности с низкоуровневым рантаймом: **`myrunc` остаётся полностью изолированным компонентом**, как и `runc` в оригинальной архитектуре Docker, и отвечает исключительно за создание namespaces, применение cgroups-лимитов и непосредственный запуск процесса контейнера. Архитектура демона построена на чистой архитектуре.


## 📋 CLI Reference

Текущий функционал `boyler-cli` покрывает полный жизненный цикл контейнера — от загрузки образа до интерактивной работы внутри контейнера и его удаления.

| Команда | Описание |
|---|---|
| `boyler-cli pull` | Загрузить образ из Docker registry |
| `boyler-cli create` | Создать новый контейнер из загруженного образа (без запуска) |
| `boyler-cli start` | Запустить созданный контейнер |
| `boyler-cli stop` | Остановить работающий контейнер |
| `boyler-cli exec` | Выполнить команду внутри контейнера и получить интерактивный shell со стримингом от демона (выход — `Ctrl+C` / `SIGTERM`) |
| `boyler-cli ps` | Показать список всех контейнеров |
| `boyler-cli inspect` | Показать подробную информацию о контейнере |
| `boyler-cli remove` | Удалить контейнер |
| `boyler-cli version` | Показать текущую версию приложения |
| `boyler-cli init` | Показать текущую версию приложения *(алиас `version`)* |
| `boyler-cli completion` | Сгенерировать скрипт автодополнения команд для указанного shell |
| `boyler-cli help` | Показать справку по любой команде |

### Типичный workflow

```bash
# 1. Загрузить образ из registry
boyler-cli pull alpine:latest

# 2. Создать контейнер из образа
boyler-cli create --name my-container alpine:latest

# 3. Запустить контейнер
boyler-cli start my-container

# 4. Зайти внутрь контейнера интерактивно
boyler-cli exec my-container /bin/sh
# выход из сессии — Ctrl+C (SIGTERM)

# 5. Посмотреть все контейнеры и их состояние
boyler-cli ps

# 6. Детальная информация о конкретном контейнере
boyler-cli inspect my-container

# 7. Остановить и удалить контейнер
boyler-cli stop my-container
boyler-cli remove my-container
```

> 💡 Все команды взаимодействуют с `boylerd` по gRPC — сам CLI не содержит логики работы с namespaces, cgroups или файловой системой, а лишь отправляет запросы демону и стримит вывод (например, двусторонний стриминг в случае `exec`).

## 📦 Установка

### Требования

- Linux, ядро с поддержкой **cgroups v2**
- Go **1.22+** (для сборки из исходников)
- `make`
- `protoc` + плагины `protoc-gen-go` и `protoc-gen-go-grpc` (нужны только если меняли `.proto`-файлы и пересобираете gRPC-код)
- Права **root** (запуск демона требует привилегий для работы с namespaces, cgroups и монтированием)
- `iproute2` для настройки сети (veth, bridge)

### Сборка из исходников

```bash
git clone https://github.com/curboturbo/boyler.git
cd boyler

# Подготовка окружения — создаёт рабочие директории
# lib/containers, lib/images и bin для собранных бинарей
make prepare

# Компиляция бинарных файлов
make compile
```

После сборки в директории `./bin/` появятся:

| Бинарь | Назначение |
|---|---|
| `boyler` | CLI-клиент |
| `daemon_boyler_linux` | gRPC-демон |
| `myrunc` | низкоуровневый рантайм |

### Регенерация gRPC-кода

Если вносились изменения в `proto/daemon.proto`, перед сборкой нужно перегенерировать Go-код:

```bash
make genproto
```

Сгенерированный код попадёт в `internal/daemon/infrastructure/inbound/api/grpc/gen`.

### Запуск

```bash
# Запуск демона (требует root — для работы с namespaces и cgroups)
cd bin
sudo ./bin/boyler init &

# Первая команда через CLI
./bin/boyler pull alpine:latest
```

### Очистка окружения

```bash
# Удаляет виртуальный сетевой bridge boyler0, витая пара удаляется при команде remove
make clean
```
## ⚙️ Конфигурация

Демон и низкоуровневый рантайм конфигурируются через `.env`-файл. Ниже — разбор всех параметров по группам.

### 📁 Пути состояния рантаймов

| Переменная | Значение по умолчанию | Описание |
|---|---|---|
| `STATE_PATH_MYRUNC` | `/var/run/myrunc` | Директория для хранения состояния контейнеров, управляемых `myrunc` |
| `STATE_PATH_RUNC` | `/var/run/runc` | Путь состояния для `runc` (совместимость / альтернативный рантайм) |
| `STATE_PATH_CRUN` | `/var/run/crun` | Путь состояния для `crun` (совместимость / альтернативный рантайм) |

> 💡 Наличие путей для `runc` и `crun` предполагает, что Boyler поддерживает (или планирует поддерживать) сторонние OCI-совместимые рантаймы как альтернативу собственному `myrunc`.

### 🗂 Пути бинарных файлов

| Переменная | Значение по умолчанию | Описание |
|---|---|---|
| `BIN_MYRUNC` | `bin/myrunc` | Путь к бинарю низкоуровневого рантайма |
| `BIN_DAEMON` | `daemon_boyler_linux` | Путь к бинарю gRPC-демона |

### 📦 Хранилище образов и контейнеров

| Переменная | Значение по умолчанию | Описание |
|---|---|---|
| `BUNDLE_PATH` | `lib/containers` | Директория с bundle-файлами контейнеров (rootfs + конфиг для рантайма) |
| `IMAGE_PATH` | `lib/images` | Директория для хранения распакованных образов |
| `UNPACK_DIR` | `lib/images` | Директория распаковки слоёв образа (совпадает с `IMAGE_PATH`) |
| `CONTAINER_DIR` | `lib/containers` | Рабочая директория контейнеров (совпадает с `BUNDLE_PATH`) |

### 🔌 Межпроцессное взаимодействие (IPC)

| Переменная | Значение по умолчанию | Описание |
|---|---|---|
| `GO_PIPE` | `go.fifo` | Именованный канал (FIFO) для передачи данных между демоном и процессом-контейнером |
| `SIGNAL_PIPE` | `signal.fifo` | FIFO для передачи сигналов (например, при `exec` / остановке) |
| `MYRUNC_META` | `state.json` | Файл метаданных состояния контейнера, который читает/пишет `myrunc` |
| `SELF_EXEC_PATH` | `/proc/self/exe` | Путь для self-exec — техника повторного запуска процесса самого себя в новых namespaces (классический паттерн контейнерных рантаймов) |

### 🌐 Сеть

Сетевая модель Boyler реализована по классической схеме виртуализации через **Linux bridge** — тот же принцип, что используется в libvirt/KVM для сети виртуальных машин, только применительно к контейнерам.

### Как это работает

1. При старте демона на хосте создаётся виртуальный **Linux bridge** (`boyler0`) с адресом `172.18.0.1/24` — он выступает точкой соединения для всех контейнеров, подобно виртуальному свитчу.
2. Для каждого запускаемого контейнера создаётся **veth-пара** — два связанных виртуальных сетевых интерфейса, один из которых (`veth_h*`) остаётся на стороне хоста и подключается к bridge, а второй (`veth_c*`) перемещается внутрь network namespace контейнера и становится его `eth0`.
3. Все подключённые к bridge контейнеры получают адрес из подсети `172.18.0.0/24` и могут обмениваться трафиком друг с другом напрямую через bridge — как хосты в одном L2-сегменте.
4. Для выхода во внешнюю сеть трафик с bridge маршрутизируется через физический интерфейс хоста (`DEFAULT_ETH0`) — для этого на хосте включается **IP forwarding** (`/proc/sys/net/ipv4/ip_forward`).
5. Каждому контейнеру прописывается DNS-сервер (по умолчанию `8.8.8.8`) в `/etc/resolv.conf` внутри его rootfs — так контейнер может резолвить внешние имена.

### Схема адресации

| Параметр | Значение |
|---|---|
| Bridge-интерфейс | `boyler0` |
| IP моста на хосте | `172.18.0.1/24` |
| Подсеть контейнеров | `172.18.0.0/24` |
| Префикс veth на хосте | `veth_h*` |
| Префикс veth в контейнере | `veth_c*` |
| DNS по умолчанию | `8.8.8.8` |

> 💡 Каждый контейнер получает изолированный `network namespace` — у него собственный стек: интерфейсы, таблица маршрутизации, ARP-таблица. Наружу он "видит мир" только через свой конец veth-пары, подключённый к общему bridge хоста.

### 🧩 Системные пути

| Переменная | Значение по умолчанию | Описание |
|---|---|---|
| `PROC_PATH` | `/proc` | Путь к procfs — используется для монтирования `/proc` внутри контейнера |
| `SYSTEM_PATH` | `/sys/fs/cgroup` | Корень cgroups v2 на хосте |
| `CGROUP_PATH` | `boyler_restrictions` | Имя cgroup-группы, в которую помещаются все контейнеры Boyler для применения лимитов ресурсов |

### 🔗 API и мониторинг

| Переменная | Значение по умолчанию | Описание |
|---|---|---|
| `UNIX_SOCKET` | `/tmp/daemon_grpc.sock` | Unix-сокет, через который CLI взаимодействует с демоном по gRPC |
| `HTTP_PPROF_SOCKET` | `127.0.0.1:6060` | Адрес для `pprof` — профилирование производительности демона (CPU, память, горутины) |
| `DAEMON_LOG_PATH` | `/var/log/boyler_daemon.log` | Путь к лог-файлу демона |

### ℹ️ Версия и платформа

| Переменная | Значение по умолчанию | Описание |
|---|---|---|
| `VERSION` | `Boyler_v1.0` | Версия приложения, отображается в `boyler-cli version` |
| `OS` | `linux` | Целевая ОС сборки |
| `ARCHITECTURE` | `amd64` | Целевая архитектура сборки |

### Пример `.env` для локального запуска

```dotenv
# Минимальный набор для быстрого старта
STATE_PATH_MYRUNC="/var/run/myrunc"
BIN_MYRUNC="bin/myrunc"
BIN_DAEMON="daemon_boyler_linux"
BUNDLE_PATH="lib/containers"
IMAGE_PATH="lib/images"
UNIX_SOCKET="/tmp/daemon_grpc.sock"
BRIDGE_NAME="boyler0"
BRIDGE_IP="172.18.0.1/24"
CONTAINER_LOCAL_NETWORK="172.18.0.0/24"
DEFAULT_ETH0="eth0"
DAEMON_LOG_PATH="/var/log/boyler_daemon.log"
```
